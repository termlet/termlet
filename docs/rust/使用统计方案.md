# 使用统计方案

> 作者：ruan
> 日期：2026-10-29
> 状态：已定（2026-10-29）：第 7 节的问题除第 3 项外都按推荐；第 3 项改为**要**统计国家或地区（由接收端读 Cloudflare 按 IP 推断的两位代码，见 2.2）；之后又定了 `api.termlet.dev` 也由 Cloudflare 按 IP 限速（第 15 项、3.9）；客户端做完后定了**不提示**（第 6 项、5.1）。0.1.0 起实施，客户端的实现见[技术方案](技术方案.md)第 12 章的“使用统计”。
> 2026-11-22 用户定加功能名单 `features`（只记上次发送以来用过哪些功能，没有次数），见 2.2、2.3、3.2、3.7、4.1、5.3 与第 7 节第 16 项。
> 已定（用户 2026-10-28）：要做、**默认开**；首次启动时明确告知（2026-10-29 改为不提示，见 5.1）；设置中一键关闭；可以查看将发送的原文；不存 IP、不带设备 ID；官网隐私说明写清楚；自己写接收端（Cloudflare Worker，`api.termlet.dev`，与崩溃上报共用），不接境外第三方 SDK；先只做每天一次的匿名活跃统计。

## 0. 方案摘要（已定）

客户端每天（UTC）最多发一条，正文只有格式版本、Termlet 版本、系统与大版本、CPU 架构、界面语言、使用时长档位，外加“本周 / 本月第一次发送”两个标记（不带任何 ID 也能算出周活、月活，做法参照 Fedora 的 countme），以及上次发送以来用过哪些功能（固定清单中的名称，没有次数与时间，2026-11-22 加）。本机只记两个日期（第一次、上次发送）与还没发出的功能名单，不记时刻、不记 ID。**不另外提示**（用户 2026-10-29 看过界面后定）：默认开、照常发送，只在安装包许可说明的第四节、官网的隐私说明与设置“关于 → 隐私”中写明，用户随时可以在设置中关闭、查看将发送的内容。开关放在“设置 → 关于”新的“隐私”一组（与“自动发送崩溃报告”放在一起），只对这台电脑生效。接收端（自己写的程序，运行在 Cloudflare Workers 上，与崩溃上报共用）的 `POST /v1/stats`：不读 IP 与 User-Agent，`request.cf` 只读 Cloudflare 按 IP 推断的国家或地区（两位代码，客户端不多发字段），城市、经纬度、ASN、时区等其余各项不读；防刷靠 Cloudflare 在边缘按 IP 限速（Worker 不参与，被拦的请求会连同 IP 短期留在 Cloudflare 的安全日志中）与每天上限；不写请求日志，收到后**只把各项（含国家或地区）分别加到当天的计数上、不保存这条统计本身**，按天的计数保留 400 天，之后只留按月的总数。命令行工具 `termlet` 不发。

几个可以借鉴的做法（不是 SSH 客户端，但做法有代表性）：

| 产品 | 做法 |
|---|---|
| **Homebrew** | 默认开；发送第一条之前先显示告知，用户可以先关；请求中**没有用户标识也没有 IP 字段**；存在自建的 InfluxDB，**保留 365 天**；`brew analytics off` 或 `HOMEBREW_NO_ANALYTICS=1` 关闭，`HOMEBREW_ANALYTICS_DEBUG=1` 打印发出的请求；汇总数据公开 |
| **Fedora DNF countme** | 不用 machine-id 或任何 UUID 也能数出每周有多少台系统：每周随机挑一次本来就要发的元数据请求带上 `countme=N`，N 是系统年龄的档位（1：第一周，2：第一个月，3：前六个月，4：六个月以上） |
| **ShellRS**（同为 GPUI 的 SSH 客户端） | 默认开，“设置 › 关于 › 隐私”中的“发送匿名使用统计”；经 Aptabase（美国区）发 `app_installed`、`app_started`、`app_active`（每个 UTC 日第一次切到前台）与每 4 小时汇总的功能使用次数，带版本、系统名与版本、架构、安装方式、外观、语言、主题、若干开关与主机等数量的档位；不带设备 ID，Aptabase 用 IP + User-Agent + 每天更换的盐算散列区分设备、按 IP 推断国家，不存 IP；开发构建与外部 CLI 不发。手册与代码中没看到首次启动的告知，也不能查看原文 |
| **Termora** | 经 Mixpanel 每次启动发 `launch`，带系统、平台、版本、语言与存在数据库中的随机 UUID；没有开关；依次试 `api-eu`、`api-in`、`api` 与**明文 http** 的端点（读的是本机的源码副本，2026-10-08） |
| **Termark** | 闭源；据公开资料遥测默认开，细节查不到 |

结论：
- 默认开、可以关是主流（Tabby、VS Code、Zed、Warp、Homebrew、ShellRS）；重视隐私的产品要么不收（Obsidian、MobaXterm），要么让用户主动选（1Password 个人版）。Termlet 选默认开，就要靠“收得少、看得见、好关”换回信任。
- 值得学的：Homebrew（不带 ID、告知先于发送、能打印请求、写明保留期）；VS Code、Zed、Warp（能看原文）；Zed（首次引导中直接给开关）；Fedora（不带 ID 的去重）。
- 要避开的：持久的随机 ID（Tabby、Termora、Zed）；第三方 SDK（Tabby、Termora、Termius，Warp 2026-10 经第三方供应商泄露了约 1% 用户的 agent 记录与遥测数据——存了的东西才会泄露）；不能关（Termora）；明文 http（Termora）；收 MAC、邮箱用于营销（Xshell）；把开关和功能绑在一起（Warp 免费版的 AI）。
- 比 ShellRS 多做的：查看原文、不经第三方、接收端不读 IP（国家或地区同样按 IP 推断，但由 Cloudflare 边缘给出代码，我们的程序碰不到 IP）、服务器只存计数。

## 2. 收集的内容

### 2.1 现状（客户端已经发出去的）

- 检查更新、远程配置、崩溃上报、WebDAV 的请求都带 `User-Agent: Termlet/<版本>`（[update/http.rs](../../crates/termlet-core/src/update/http.rs) 第 21 行、[crash/mod.rs](../../crates/termlet-core/src/crash/mod.rs) 第 777 行、[cloudsync/webdav.rs](../../crates/termlet-core/src/cloudsync/webdav.rs) 第 60 行），此外没有别的标识。检查更新的地址不带参数；更新源现在是 GitHub Releases，以后是 R2，两边我们都看不到访问日志，所以分发侧只能看到下载次数。
- 崩溃报告（默认关闭）带版本、`platform`、`arch`、`os_release`（Windows 的完整版本号，如 `10.0.26200.6899`）、随机的报告 ID 与精确时间，写入前已脱敏（[crash/mod.rs](../../crates/termlet-core/src/crash/mod.rs)、[diag/scrub.rs](../../crates/termlet-core/src/diag/scrub.rs)）。使用统计**不复用**这套字段：崩溃需要精确版本与时间，统计不需要。
- 系统信息由 [diag/system.rs](../../crates/termlet-core/src/diag/system.rs) 读出（Windows 读注册表的版本号、ProductName、DisplayVersion），统计在它的基础上只取粗粒度。

### 2.2 第一版的字段（已定）

| 字段 | 例子 | 为什么要 | 粒度 | 识别个人的风险 |
|---|---|---|---|---|
| `v` | `1` | 正文的格式版本，以后加字段时接收端据此校验 | 整数 | 无 |
| `app` | `0.1.0` | 版本分布、新版本推开的速度；决定什么时候可以不再兼容旧的数据格式 | 完整版本号（含预发布后缀） | 单独看低。长期不升级的极少数人会在某个旧版本上“独一份”，但只知道“有一台没升级” |
| `os` | `windows` | 平台投入（Linux、macOS 没有真机测试，有多少人用决定投入多少） | `windows` / `macos` / `linux` | 无 |
| `osVersion` | `11 25H2` | 最低支持哪个系统版本、ConPTY 等随系统变化的行为要在哪些版本上测 | Windows：构建号 ≥ 22000 为 `11`，否则 `10`，加注册表的 DisplayVersion（`22H2`、`24H2`、`25H2`，读不到时只写大版本），**不含**构建号、月度补丁号（UBR）与家庭版 / 专业版；macOS：只到大版本（`15`、`26`）；Linux：`/etc/os-release` 的 `ID` 在白名单（ubuntu、debian、fedora、arch、opensuse、linuxmint）内时写 ID 与版本号（`ubuntu 24.04`、`debian 12`、`arch`），其余一律 `other` | 低：每个平台只有几种取值 |
| `arch` | `x86_64` | 要不要出 Windows / Linux 的 ARM 版 | `x86_64` / `aarch64` | 低。Windows on ARM 少，组合起来显眼（见下） |
| `lang` | `zh-CN` | 翻译投入（繁体刚加上） | 实际使用的界面语言：`zh-CN` / `zh-TW` / `en` / `ja` / `ko`（设置为“跟随系统”时取解析后的那个；`ja`、`ko` 是后加的，0.3.0 及以前的客户端把日文、韩文界面记为 `en`），**不发**系统区域设置 | 低 |
| `age` | `m1` | 新增与留存：每天有多少新装的、用了一个月的还剩多少 | 从本机第一次发送成功的日期算起（UTC 日）：当天 `new`，1–6 天 `w1`，7–29 天 `m1`，30–179 天 `m6`，180 天以上 `old`（参照 Fedora countme）；本机记的日期不发出去 | 低：5 档 |
| `firstOfWeek` | `true` | 不带 ID 算周活：一周内这个标记为真的条数就是这一周用过的电脑数 | 布尔：这是本周（ISO 周，周一开始，UTC）第一次发送成功 | 无新信息 |
| `firstOfMonth` | `false` | 同上，算月活 | 布尔：本月（UTC）第一次 | 无新信息 |
| `features`（2026-11-22 加） | `["ssh","sftp","port_forward"]` | 哪些功能有人用、哪些可以不花力气（冻结、收起还是继续做） | 上次发送成功以来用过的功能：固定清单中的名称（51 项，名称发布后不改），按清单的顺序，没有次数、时间与先后；什么都没用过时为 `[]`，照样发。清单与判定点见[用户指南的“使用统计”](../guide.md#使用统计) | 低到中：每项只是布尔，但组合起来比其他字段多；接收端只按名称分别计数、不存名单、不与任何字段交叉（4.1） |
| `country`（**接收端推断**，客户端不发） | `CN` | 大致的使用国别：国内外用户的比例，决定下载源与国内加速、各语言版本的投入 | 接收端只读 `request.cf.country`（Cloudflare 按连接的 IP 查自己的地理库得出的两位代码，与 `CF-IPCountry` 请求头相同），只记这个代码；IP 与 `request.cf` 的其余各项（城市、地区、邮编、经纬度、时区、ASN 与运营商、机房）不读、不存 | 中：取值多（几十到上百个），是各项中最有区分度的；按天计数、不存单条，见下 |

“当天是否活跃”就是这条统计本身：当天（UTC）窗口获得过焦点，或者处理过命令行工具的请求（由 `termlet` 在后台拉起、没有窗口时），就算用过。

**国家或地区的取值与准确度**：
- 记的是 ISO 3166-1 的两位代码（`CN`、`TW`、`HK`、`US`……），界面与报表中一律叫“国家或地区”。接收端只接受 `^[A-Z]{2}$`，其余（没有 `request.cf`，如本机开发与测试；值不合格）记为 `XX`。
- Cloudflare 的两个特殊值照原样记，报表中单独列出：`XX`（没有国家数据，未知）、`T1`（Tor 网络；社区反馈有一部分 Tor 出口没被认出，会显示为出口所在的国家）。见 [Cloudflare HTTP headers（CF-IPCountry）](https://developers.cloudflare.com/fundamentals/reference/http-headers/)、[Workers 的 Request（`request.cf.country` 与 `CF-IPCountry` 相同）](https://developers.cloudflare.com/workers/runtime-apis/request/)。
- 准确度：按的是连到 Cloudflare 的那个 IP，Cloudflare 自己说 IP 地理位置是估计、不保证准确（[IP geolocation](https://developers.cloudflare.com/network/ip-geolocation/)）。走代理、VPN、公司网络出口时记的是出口所在的国家；Termlet 的 HTTP 客户端跟随系统代理（3.4），国内开着系统代理的用户多半会记成香港、日本、新加坡、美国等，**国内的比例会偏低**，看比例时与 `lang=zh-CN` 对照着看。
- 客户端不发这一项，正文里有 `country` 字段也忽略（不能由客户端指定）；“查看内容”中说明接收端会另外推断它（5.3）。

**组合起来会不会变成指纹**：各字段单独看都识别不了人，但组合的种类不少——几个版本 × 七八种系统版本 × 2 种架构 × 5 种语言 × 5 个档位，有上千种组合，再乘上几十个国家或地区就是几万种。用户只有几千时，很多组合只有一两台电脑：如果服务器把每条统计整条存下来，“在冰岛、用繁体、ARM 版 Windows、一直停在 0.1.2 的那一台”每天的使用轨迹就能单独挑出来（GDPR 所说的 singling out）。虽然仍然不知道是谁，但没有必要留这种可能。所以：
- 接收端**不存整条**，只把各项分别加到当天的计数上（“今天 `app=0.1.0` 加 1”“今天 `lang=zh-TW` 加 1”“今天 `country=IS` 加 1”），见 4.1。数据库里没有能把几项拼回同一台电脑的记录。
- 国家或地区也只是一个单独的计数：某个国家只有一台电脑时，它的日计数等于“那个国家有一台电脑在这些天用过”，但拼不回这台电脑的版本、系统、语言，更不知道是谁。报表中少于 5 台的国家可以合并成“其他”显示（数据库照存，只是看的时候不单列）。
- 只多保留一张交叉表 `os × app`（判断某个版本在某个平台上推不开，例如自动更新在 macOS 上出了问题）；`os` 只有 3 种取值，风险低。**国家或地区不与任何字段交叉**。其他交叉以后真需要时再加，并在隐私说明中写明。
- 字段只用固定的几种取值，接收端按白名单校验，不认识的值不存（计入 `other`），防止有人借字段塞进别的内容。

请求头只有 `Host`、`User-Agent: Termlet/<版本>`（与现在检查更新的相同）、`Content-Type`、`Content-Length` 以及 HTTP 库默认的 `Accept` 之类，不带 Cookie、不带认证。接收端连 User-Agent 也不读；Cloudflare 转给 Worker 的请求中有 `CF-Connecting-IP` 头，Worker 不读它，国家或地区由 Cloudflare 在边缘查好放进 `request.cf.country`。

### 2.3 以后可选（每加一项都要先改隐私说明、安装包的许可说明与设置中的说明，并在更新日志中写明，见 5.1）

| 内容 | 用途 | 做法 |
|---|---|---|
| ~~功能使用次数~~ | 哪些功能有人用、哪些可以不花力气 | **2026-11-22 已做，改为只记用没用过**（不按次数分档）：见 2.2 的 `features` |
| 设置摘要 | 默认值合不合适 | 只发固定取值：主题深浅、云同步是否开启（文件夹 / WebDAV，不含位置）、应用锁是否开启、命令行工具是否开启 |
| 数量档位 | 用户的规模（主机多的人的界面要不要另做） | 主机、凭据、端口转发、快捷命令各有多少，只报档位：0、1–5、6–20、21–100、100 以上（ShellRS 的做法） |
| 昨天是否出过崩溃 | 没开崩溃上报的人也能算出“无崩溃的电脑占比” | 布尔，只看本机有没有新的崩溃记录，不发记录内容 |
| 启动耗时 | 发现性能回归 | 档位（< 0.5 秒、0.5–1、1–2、2–5、> 5 秒） |
| 安装方式 | 等有了便携版、winget 再加；现在每个平台只有一种，与 `os` 重复 | `installer` / `portable` / `winget` / `tar` / `app` |
| Windows 的版本类型 | 企业版、教育版占比 | `home` / `pro` / `enterprise` / `education` / `other` |

### 2.4 绝不收

- 主机地址、主机名称、端口、用户名、跳板与代理、主机指纹、密钥与凭据（含指纹、类型、数量以外的任何信息）。
- 命令、终端的输入输出、剪贴板、快捷命令的内容、命令历史、审计日志、会话日志。
- 文件名、路径、传输的文件、SFTP 浏览过的目录、云同步的位置与 WebDAV 地址。
- IP 地址（接收端不读、不存）；比国家或地区更细的位置：`request.cf` 中只读 `country` 一项，城市、地区、邮编、经纬度、时区、大洲、ASN 与运营商、Cloudflare 机房等其余各项一律不读、不存。
- 任何持久的标识：设备 ID、安装 ID、随机 UUID、数据目录 ID（钥匙串账户名中用的那个）、MAC 地址、机器 GUID、硬盘序列号、计算机名、系统用户名、域、账号（Termlet 没有账号）。
- 精确时间：客户端正文中没有时间，服务器只按收到时的 UTC 日期计数；也不发时区。
- 屏幕分辨率与缩放、显卡、已安装的其他软件、环境变量、代理设置、本地终端的命令行、自定义规则的内容。
- 崩溃内容（那是单独的、默认关闭的崩溃上报）。

## 3. 发送方式

### 3.1 什么时候发

- 发送的条件（全部满足）：开关开着（默认开，不另外提示，见 5.1）；不是调试构建；没有被环境变量或远程配置关掉（3.6）；今天（UTC）有活跃（2.2）；今天还没有发送成功。
- 检查的时机：启动后主窗口显示（应用锁解锁之后）时在后台检查一次，之后每小时一次（与检查更新的定时器 `UPDATE_POLL` 共用）；窗口获得焦点、处理命令行工具的请求时记下“今天活跃”。
- 为什么按 UTC 判断“今天”：服务器按收到时的 UTC 日期计数，客户端也按 UTC，同一台电脑在服务器的同一天最多一条，日活就是当天的条数。对北京时间的用户来说一天是早上 8 点到第二天早上 8 点，不影响统计。
- 时钟被往回调（上次发送的日期比今天晚）时按“今天还没发”处理，并把“本周 / 本月第一次”当作真。

### 3.2 本机记什么、不记什么

`{数据目录}/usage.json`（与 `remote-config.json` 同一类，不在数据库中、不同步、不进备份）：

```json
{ "v": 1, "since": "2026-10-29", "lastSent": "2026-11-02" }
```

- `since`：第一次发送成功的 UTC 日期，用来算 `age`；`lastSent`：上次发送成功的 UTC 日期，用来判断今天是否已发、是不是本周 / 本月第一次。
- `{数据目录}/usage-features.json`（2026-11-22 加）：还没发出的功能名单，如 `{"v":1,"features":["ssh","sftp"]}`，只有名称。某一项第一次用到时写入，发送成功后去掉已发出的（空了就删除），重启后读回；设置关着、被环境变量关掉、调试构建时不记。
- 不记：发送的时刻、发送的历史、任何 ID、服务器的回应、功能用了几次与什么时候用的。
- 每次发送成功在程序日志中写一行 info（含发出去的 JSON 原文）。日志在本机、保留 14 天，这就是“发过什么”的记录，排查时也能看到。

### 3.3 失败与重试

- 网络错误、10 秒超时、HTTP 5xx、429：留到当天的下一次检查（每小时）再试。
- 其他 4xx（格式不对等）：当天不再试，等下一个版本修。
- 跨过 UTC 零点还没发成功的，**不补发**前一天的（正文中没有日期，补发会算到新的一天）；前一天就算没记上。
- 发不出去不影响任何功能、不弹提示、不积压；日志中同一天只记第一次失败（避免离线时每小时一行）。

### 3.4 离线、内网

离线、内网、公司代理拦截时照常使用，只是这几天没有记上。HTTP 客户端与检查更新相同：走系统与环境变量中的代理（公司代理能看到访问了 `api.termlet.dev`，看不到 HTTPS 的内容）。

### 3.5 关闭

- 设置中关掉（保存后）立即生效：之后不再发送，正在进行的那一次不取消（只有几百字节）；`usage.json` 删除，本机不再保留统计用的任何记录。
- 再打开时从头算：`age` 为 `new`（新增会多算一台，开关来回切的人很少，接受）。
- 关闭期间的不补发。

### 3.6 其他关闭途径

- 环境变量 `TERMLET_USAGE_URL=off`（与现有的 `TERMLET_UPDATE_URL`、`TERMLET_CRASH_URL` 一致；公司可以用组策略统一设置）；指向本机回环地址的 http 地址时发到那里（测试用，调试构建也发）。
- 环境变量 `DO_NOT_TRACK=1`（[Console Do Not Track](https://consoledonottrack.com/) 的约定）。
- 被环境变量关掉时，设置中的开关显示为关、不能改，下面说明“已由环境变量 … 关闭”。
- 远程配置（已有签名，见 [remote_config.rs](../../crates/termlet-core/src/remote_config.rs)）加 `usageUrl`：没有这一项时用内置地址 `https://api.termlet.dev/v1/stats`；为 `"off"` 时所有客户端停发（发布方的总开关，例如接收端出了问题）；为其他 https 地址（不带账号）时改用它。内置地址的原因：远程配置现在在 GitHub Pages，国内时通时不通，统计不能依赖它才发。
- 调试构建不发（`cargo run` 的数据目录是 `termlet-dev`），UI 测试与单元测试也不发。

### 3.7 请求格式

```http
POST /v1/stats HTTP/1.1
Host: api.termlet.dev
User-Agent: Termlet/0.1.0
Content-Type: application/json
Content-Length: 140

{"v":1,"app":"0.1.0","os":"windows","osVersion":"11 25H2","arch":"x86_64","lang":"zh-CN","age":"m1","firstOfWeek":true,"firstOfMonth":false}
```

回应：成功 `204 No Content`，没有正文。

2026-11-22 起正文的最后多一个 `features`（格式版本仍是 1：接收端以前的版本忽略不认识的字段，照样收下其余各项）：

```json
{"v":1,"app":"0.3.3","os":"windows","osVersion":"11 25H2","arch":"x86_64","lang":"zh-CN","age":"m1","firstOfWeek":false,"firstOfMonth":false,"features":["ssh","split","sftp","port_forward","host_tools","cli"]}
```

为什么是“上次发送以来”而不是“今天”：统计在当天第一次用到 Termlet 时就发出，那时当天几乎什么都还没用；名单留到下一次发送时带上，接收端按收到的那天计数，比实际使用晚一天左右。

### 3.8 不带设备 ID 怎么大致去重

去重在客户端做：每台电脑（准确说是每个数据目录）每天最多一条。于是：

| 指标 | 算法 |
|---|---|
| 日活 | 当天的条数 |
| 周活 | 一周（周一到周日，UTC）内 `firstOfWeek` 为真的条数之和 |
| 月活 | 一个月内 `firstOfMonth` 为真的条数之和 |
| 每天新增 | `age=new` 的条数 |
| 留存（粗略） | 各档位的月活：例如本月 `age=m1`、`m6` 的月活与上月、前几个月的新增相比 |

误差来源（统计只看趋势，不追求精确）：
- 多算：同一台电脑的几个数据目录（`TERMLET_DATA_DIR`，调试构建不发）；删掉数据目录、开关关了再开（算作新的一台）；服务器收下了但回应丢了、客户端重发；伪造的请求（4.2 的上限能挡住大量的）。
- 少算：离线、内网的日子；国内访问 Cloudflare 不稳（国内用户偏少，看比例时要记得）；关了的人。
- 统计的是电脑，不是人：一个人两台电脑算两台。
- 国家或地区按出口 IP：代理、VPN、公司出口会记成出口所在的国家（2.2）。

### 3.9 怎样做到不存 IP，能做到什么程度

我们能保证的（都在接收端）：
- 接收端不读取 `CF-Connecting-IP`、`X-Forwarded-For`、`X-Real-IP`、`User-Agent` 等请求头；`request.cf` 只读 `country` 一项（城市、经纬度、ASN、时区等其余各项不读）。国家代码是 Cloudflare 在边缘按 IP 查好的，接收端拿到的只是两位代码，代码中没有任何读 IP 的地方；崩溃上报连 `request.cf` 都不读。接收端的测试构造带城市、经纬度的 `request.cf`，核对存下的只多了国家代码。
- 不写请求日志：Workers 的调用日志会带请求头（含 `cf-connecting-ip`）与 `request.cf`，所以关掉，也不推送日志；排查时只临时看实时日志，不落盘。
- 存储中没有 IP，也没有单条统计（4.1）；国家或地区只是按天的一个计数项。
- 按 IP 的限速在 Cloudflare 边缘做，接收端不参与（用户 2026-10-29 定）：一条限速规则同时管下载站 `dl.termlet.dev` 与 `api.termlet.dev`（崩溃上报、使用统计都在内），同一 IP 短时间内请求过多时暂时拦下。被拦的请求到不了接收端，接收端照旧不读 IP。正常使用远到不了这个频率（统计每天一条、崩溃报告很少；公司、学校同一个出口 IP 后面的人再多，发送也分散在一天中）；被拦时 Cloudflare 回 429，客户端按 3.3 当天稍后再试。

我们做不到的：
- Cloudflare 作为网络服务商在 TLS 终止、转发、防攻击时必然处理 IP（按 IP 查国家也是它做的，每个经过它的请求本来都会查），按它的隐私政策作为数据处理者（data processor）处理，具体保留多久它没有写明。隐私说明照实写这一点。
- 被上面的限速规则拦下的请求，会作为安全事件连同 IP 出现在 Cloudflare 的安全日志中，短期留存（保留期由 Cloudflare 定），只有 Cloudflare 账号的所有者能看到；我们不导出、不另存。隐私说明中统一写：“为防滥用，Cloudflare 会按网络地址限制请求频率；被拦下的请求会在 Cloudflare 的安全日志中短期留下网络地址，Termlet 不读取、不保存。”（6.1）
- 公司代理、运营商能看到访问了 `api.termlet.dev` 这个域名。

## 4. 接收与存储

接收端是自己写的程序（不在本仓库，运行在 Cloudflare Workers 上，与崩溃上报共用）。这里只写与隐私有关、客户端要配合的约定。

### 4.1 只存计数

- 收到一条统计后，把各项分别加到当天（收到时的 UTC 日期）的计数上：总条数，`app`、`os`、`osVersion`、`arch`、`lang`、`age`、国家或地区各一项，`firstOfWeek`、`firstOfMonth` 为真时各一项，外加 `os × app` 的交叉（2.2）；这条统计本身不保存。
- 功能名单（2026-11-22 加）：名单中每个名称在当天的计数上各加 1，另记“带了名单的条数”作占比的分母；名单本身不保存，不与版本、系统、国家等任何一项交叉；接收端清单中没有的名称忽略。每天为功能写的行数有上限（防刷时不超出免费额度），到了之后的统计只计基本的各项。
- 按天的计数到期前汇总成按月的总数。
- 不选“每条存一行、事后任意分析”的存法：隐私说明能写“服务器上只有每天的计数，没有单条记录”；代价是要看新的交叉只能改代码、只对之后的数据有效，第一版要看的指标（3.8）都是事先能定的，够用。

### 4.2 校验与防刷

- 只收 `POST`、`application/json`，正文不超过 1 KB。
- 字段按白名单校验：`v` 为 1；`app` 匹配 `^\d+\.\d+\.\d+(-[0-9A-Za-z.]+)?$` 且不超过 32 个字符；`os`、`arch`、`lang`、`age` 是枚举；`osVersion` 按平台的格式（Windows `^(10|11)( \d{2}H\d)?$`，macOS `^\d{2}$`，Linux 白名单）；两个标记是布尔。不认识的字段忽略、不存（正文中的 `country` 也忽略，国家或地区只取 `request.cf.country`）；值不合格时整条返回 400。
- 枚举加取值（如 2026-11 `lang` 加 `ja`、`ko`，Linux 白名单加发行版）：两边一起改，**先部署接收端，再发布发送新值的客户端**。顺序反了，新客户端的统计整条被拒（400），客户端当天不再发，那几天的统计就丢了。客户端的取值在 `termlet-core` 的 `usage` 模块（`LANGS` 等），它的测试照搬了接收端的校验。
- 防刷：Cloudflare 在边缘按 IP 限速（3.9）；接收端另有每天收下条数的上限，超过的只记丢弃的条数、照样回 204（回 429 只会让客户端每小时再来一次）。统计只用来看趋势，被刷了也只是数字不准。

### 4.3 保留多久

| 数据 | 保留 | 理由 |
|---|---|---|
| 原始请求 | 不保存（只在内存中处理） | 没有必要；不存就不会泄露 |
| 按天的计数 | 400 天 | 与崩溃上报的计数一致；够做同比（13 个月）；也在法国 CNIL 对免同意的受众测量要求的“最多 25 个月”之内（6.2） |
| 按月的总数 | 长期 | 只是全体的月度总数，没有能识别任何电脑的信息；看长期趋势用 |

不做公开的查询接口。以后可以考虑像 Homebrew 那样在官网公开汇总（第 7 节问题 11）。

## 5. 告知与设置

### 5.1 怎么告知用户：不提示（用户 2026-10-29 看过界面后决定）

原方案是首次打开主窗口时显示不自动消失的通知（知道了 / 查看内容… / 不发送），处理之前一条都不发；客户端照此做完后，用户看过界面，改为**不提示**：不显示首次告知，默认开，照常按 3.1 的规则发送。用户从这几处知道发什么、怎么关：
- 安装包许可说明的第四节（Windows 安装程序的许可页中显示，各平台的包中都有，6.1）；
- 官网的隐私说明，以及用户指南（[使用统计](../guide.md#使用统计)）；

### 5.4 关闭后的行为

见 3.5：保存后立即停止，不补发，删除 `usage.json`；被环境变量关掉时开关不能改；远程配置的总开关关掉时开关照常显示（这是发布方暂停，不是用户的选择），说明“暂停发送”。

### 5.5 命令行工具 `termlet` 是否统计

建议**不发**：
- 它只依赖 `termlet-proto`，本身不联网；加统计就要给它加 HTTP 与状态文件，违背它“小、可审计”的定位。
- AI 工具一天可能调用上百次，用户（和他们的公司）不会预期一个命令行工具在后台联网。
- 它必须由 Termlet 处理请求，Termlet 当天就算活跃，应用这边已经记上了；以后要看命令行用得多不多，在应用这边按命令类别计数（2.3 的功能使用次数）。
- 由 `termlet` 在后台拉起、没有窗口的 Termlet 照常按 3.1 发。
- ShellRS 也是外部 CLI 不发。

## 6. 合规与文案

### 6.1 告知的文案

对外的说明以这几处为准，改收集的内容时一起改：安装包许可说明的第四节（`packaging/windows/license_zh_CN.txt`、`license_zh_TW.txt`、`license_en.txt`，各平台的包都带）、官网的隐私说明（https://termlet.dev/privacy/ ）、用户指南的“使用统计”（`docs/guide.md` 与 `docs/guide.en.md`）、设置“关于 → 隐私”的说明（5.2）。限速的说明各处统一用这一句：“为防滥用，Cloudflare 会按网络地址限制请求频率；被拦下的请求会在 Cloudflare 的安全日志中短期留下网络地址，Termlet 不读取、不保存。”

### 6.2 法律上要注意的（简要，不是法律意见）

**中国大陆（《个人信息保护法》）**
- 第四条：个人信息“不包括匿名化处理后的信息”；第七十三条：匿名化是指“个人信息经过处理无法识别特定自然人且不能复原的过程”，去标识化（借助额外信息仍能识别）的仍是个人信息。所以关键是做到真正匿名：不带任何持久标识（带了随机 ID 就只是去标识化），服务器只存分项计数。
- 传输时 IP 地址会经过：国家标准 GB/T 35273-2020 附录 A 把 IP 地址列为个人信息（网络身份标识信息）的例子。我们的程序不读不存；Cloudflare 是境外服务商，转发、按 IP 限速时会处理 IP（被拦下的请求短期留在它的安全日志中），是否算“向境外提供个人信息”有解释空间。个人开发的免费软件、不保存，风险低，但隐私说明中写明 Cloudflare 更稳妥（官网的隐私说明已写）。国家或地区是 Cloudflare 按 IP 查出的，我们只拿到并按天计数两位代码，计数本身识别不了人。
- 即使主张是匿名信息，也按第十七条的告知要求写隐私说明（处理者的姓名和联系方式、目的、方式、种类、保存期限、怎么行使权利），成本低。

**欧盟（GDPR 与 ePrivacy 指令）**
- GDPR 序言第 26 条：匿名信息不适用 GDPR，存下的计数属于这一类。但收到请求的那一刻，IP 地址是个人数据（欧盟法院 Breyer 案 C-582/14 认为动态 IP 可以是个人数据），这部分处理（含 Cloudflare 按 IP 推断国家或地区、按 IP 限速防滥用）可以以正当利益（第 6 条第 1 款 f 项）为依据，并在隐私说明中写明（第 13 条），需要写明处理者与联系方式（官网的隐私说明写了 hi@termlet.dev）。
- ePrivacy 指令第 5 条第 3 款（“Cookie 条款”）：EDPB 2/2023 指南（2024-10 定稿）认为，装在设备上的软件主动把设备上的信息发给服务器，也属于“获取终端设备中的信息”，原则上需要同意，除非是提供服务所“严格必要”的；统计通常不算严格必要。各国执行不一：法国 CNIL 给只做受众测量、只产生匿名统计、不与其他数据交叉、不跨网站或应用追踪、告知用户、数据最多保存 25 个月等条件全部满足的统计开了免同意的例外，网站与移动应用都适用。
- 结论：默认开在欧盟有一定争议（Homebrew、VS Code、Zed 也是默认开）。本方案尽量贴近 CNIL 的例外条件（目的单一、只产生匿名计数、不交叉、保存 400 天、一键关闭）；“告知用户”一条靠安装包的许可说明、隐私说明与设置中的说明，去掉首次告知（5.1）后不再有“处理告知前不发”。如果以后欧盟用户多或收到投诉，可以按本机的系统区域（只在本机判断、不发出去）在欧盟地区加首次询问、默认不发。
